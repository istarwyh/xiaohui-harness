# Agent Note: XiaoHui product workbench distribution

Status: implemented

English | [中文](2026-08-22-xiaohui-product-workbench.zh.md)

## Problem

Installing a domain plugin after installing a generic Harness desktop still asks the user to understand profiles, package registries, Python environments, Skills, and adapter paths. The Harbor integration also spans a Cordis bundle and a Python runtime, so distributing only its npm package leaves a partially configured product. Reusing `~/.dsh` lowers migration cost for the generic desktop but lets a branded workbench modify another Harness installation's profiles and sessions.

## Decision

XiaoHui Harness is a product fork of the Sakana Tauri distribution with the upstream Git history retained. The reusable desktop supervision, first-run Harness provisioning, notification overlay, and updater remain in `apps/desktop-tauri`; product assembly stays in that subtree and does not change the Agent Loop or Service packages.

The committed `apps/desktop-tauri/product/harbor-evolution` snapshot contains the reviewed Harbor Cordis plugin and its `evolve-agent-with-harbor` Skill. The sibling `product/harbor-python` snapshot contains the matching Python adapter from the same stable GitHub Release. `product/dsh-codex-auth` and `product/dsh-better-sidebar` contain reviewed npm artifacts, `product/context-doctor` contains the reviewed package selected from its GitHub `main` head, and `product/personal-workbench` contains the first-party branding plugin. Every externally refreshed snapshot preserves its upstream license and records its exact version or commit, immutable archive source, integrity value, committed tree hash, and local changes in `XIAOHUI_UPSTREAM.json`; the generated `.bundle-manifest.json` records selected package versions and the whole-bundle hash consumed by the application. Peer-metadata corrections are allowed only for exact upstream versions declared in `product/plugin-update-policy.json`.

`bundle-harness-source.mjs` copies all five Cordis packages into the trimmed workspace and adds them to the bundled CLI dependency closure. The desktop overlay selects the Codex search provider, configures an existing Harbor Bundle row when present, and inserts uniquely named fallback rows for Codex Auth, Search, Image, Better Sidebar, Context Doctor, Personal Workbench, and Harbor Evolution. Each fallback disables itself when another enabled row already mounts the same package entry, so a standard Profile Bundle installed in the isolated XiaoHui Profile does not collide with the product overlay. On upgrade, native Profile repair rebinds only XiaoHui-managed `link:` dependencies that point into an older content-addressed Harness tree, then runs the standard Profile install so its lockfile and symlinks follow the active tree. Registry packages and local links outside the application's `harness-versions` directory remain untouched. First launch therefore resolves committed plugin code rather than installing changing `latest` packages. A committed product lockfile fixes the remaining production graph; the release build fetches it into a checksum-bound compressed Store, and the product-managed pnpm reconstructs `node_modules` with frozen, offline semantics.

Local release preparation is the only latest-channel refresh path and is invoked explicitly with `pnpm --dir apps/desktop-tauri run prepare:release`. It queries the latest stable npm artifacts for Codex Auth and Better Sidebar, the latest stable Harbor GitHub Release for the Cordis and Python pair, and the Context Doctor `main` head; first-party Personal Workbench remains outside the updater. The command refuses dirty managed product paths by default, with `-- --allow-dirty` as an explicit developer escape. It does not select an older fallback when the latest candidate is incompatible.

The General settings page exposes an Application updates card whose Check and update action requests the existing signed Tauri update flow. The loopback Client sends a fixed versioned message without an update URL, target version, or command name. The Tauri shell accepts it only from the active workbench iframe at the exact Host origin and invokes the one allowlisted update command. This end-user path remains separate from local release preparation: it installs a signed XiaoHui application release whose committed product snapshots already passed compatibility checks, rather than refreshing plugin source on the user's machine.

The refresh validates every policy path before reading or replacing a destination: product destinations stay below `product/`, archive source paths stay below the extracted checkout, and managed destinations are unique and non-overlapping. It downloads each archive over HTTPS with request, compressed and expanded byte, entry-count, extraction-path, and file-type checks; npm artifacts must match registry SRI, and every archive receives digest-bound provenance. It builds the prospective snapshots in a temporary staging tree, applies only exact-version peer overrides, and validates package identity, managed Node support, DSH peer ranges, the bundle patch, built Host and Client entries, Client injections, license presence, and the final tree hash. No destination changes until every external candidate passes, and any subsequent release-preparation failure restores all managed snapshots and the product lockfile. After replacement, the command rebuilds Harness from the same explicit Client environment as tagged CI, regenerates the frozen product lockfile, and proves that each DSH/Cordis peer in the lock and installed graph links to the bundled workspace rather than installing a second runtime. It then creates the digest-bound offline Store and performs the actual frozen production offline install. The Harbor commands and assembled Host run with a credential-scrubbed environment and temporary home, DSH, and temporary directories. Headless Chromium must receive every product Client bundle, activate the complete Client Loader graph without page or console errors, mount the workbench, expose the Application updates control, and pass the Context Doctor API check; the Host must also shut down normally. A successful run leaves the snapshots and lockfile for review and commit.

`prepare-xiaohui-runtime.mjs` builds a macOS arm64 resource with portable CPython 3.12, the committed Harbor Python adapter source, and Harbor. The Harbor Cordis and Python package versions must match. The generated virtual environment uses only relative interpreter links, runs directly from application resources, and is invalidated by a source-tree digest. The script accepts `XIAOHUI_HARBOR_PYTHON_SOURCE` as a temporary override. `sync-product-plugin.mjs` refreshes both committed snapshots from an extracted Harbor Release or source checkout through explicit allowlists, including the exported Harbor result schemas.

The native Host always uses `XiaoHui Harness/dsh-home` under platform application data and creates `XiaoHui Harness/workspace/jobs`; it does not adopt or import `DSH_HOME` or `~/.dsh`. This product override supersedes home adoption in [desktop host environment and home adoption](2026-08-14-desktop-host-env-and-home-adoption.md) for XiaoHui's native launch while retaining native host Node discovery and replacing global pnpm reuse with a product-managed copy. The product overlay extends [desktop shell overlay plugins](../architecture/2026-08-14-desktop-shell-overlay-plugins.md) with the required product rows; a missing Harbor runtime is a boot failure, while notification delivery remains optional. Codex Auth reads the official Codex CLI's Host-side login state and never moves tokens into browser settings. The [Job-scoped Host model bridge](../architecture/2026-08-23-harbor-host-model-bridge.md) freezes the current Agent model for Harbor Candidates and passes only a short-lived capability into the task environment, so GPT Auth remains the default Candidate model path without exporting its OAuth credential. Better Sidebar's reviewed `node-pty` build is covered by the existing workspace `allowBuilds` policy.

The native provisioner reuses Node only when its version and `process.platform:process.arch` match the product target. It never adopts a global pnpm; it provisions the pinned product copy so wrappers and native packages installed by another Node architecture cannot enter the first-launch dependency graph. macOS arm64 Node and pnpm archives are fixed by digest in source. The Store archive digest is recorded in the generated bundle manifest, verified before extraction, and removed from the writable Harness tree together with the expanded Store after a successful install. The 35,000-file Store is compressed into one resource so Tauri does not package a large mutable-looking tree or follow platform-specific links.

Private `dsh`, Node, and pnpm shims are prepended only to the Host process tree. The product does not persist a global `dsh` command or edit a shell profile by default; `XIAOHUI_PERSIST_DSH_CLI=1` is an explicit developer-only opt-in.

The desktop overlay also contributes a workbench Content Security Policy and a no-referrer policy through `webserver/index-inject`; the Tauri-owned splash and shell have their own CSP. Cordis client execution requires `unsafe-eval`, but object embedding and base-URL mutation are disabled.

The release target is `aarch64-apple-darwin` only. An `xiaohui-v*` tag consumes only the committed product snapshots and frozen lockfile; tagged CI and ordinary desktop builds do not query update channels. The workflow builds and signs the App/updater once, bundles the DMG from that App, validates the extracted updater runtime, and publishes the arm64 asset set directly from the macOS build job. This product-specific release set supersedes the platform matrix in [cross-platform desktop source provisioning](2026-08-14-cross-platform-desktop-source-provisioning.md); the underlying provisioning code remains available for future targets. Apple code signing and notarization remain separate credentials from the XiaoHui-specific Tauri updater signature.

## Alternatives considered

**Distribute only the plugin.** Rejected because users would still install and reconcile the npm bundle, Skill, Python Adapter, interpreter, and paths, which is the product burden this distribution removes.

**Build a new desktop shell.** Rejected because the Sakana shell already owns first-run provisioning, process-tree teardown, startup recovery, tray behavior, notifications, and signed updates. Reimplementation would create a second lifecycle system without adding product value.

**Download components or production dependencies on first launch.** Rejected because it makes product availability depend on npm, PyPI, a Node mirror, `uv`, and interpreter installation after the user has already downloaded the application. XiaoHui carries both domain capability and the remaining production dependency graph as fixed installer resources.

**Refresh latest plugins inside the tagged build.** Rejected because the same tag could select different source archives over time or fail after an upstream channel changes. Network refresh is an explicit local preparation step whose reviewed results become committed release inputs.

**Adopt the user's existing Harness home.** Rejected because a product application must not silently add its bundle or configuration to a separately managed Harness environment. Users can export data explicitly when a migration workflow exists.

**Keep the full upstream platform matrix.** Rejected for the first product release because the Harbor runtime resource is platform-specific and the requested delivery target is macOS arm64. Additional targets require their own portable runtime and acceptance path.

## Consequences

Installing one DMG yields a named AI workbench with an aligned Harbor plugin, Skill, Python adapter, Codex Auth, Better Sidebar, Context Doctor, and Personal Workbench already mounted. Developers refresh external product snapshots explicitly, review compatibility failures at preparation time, and reproduce a tagged release from committed plugin code, a frozen lockfile, and digest-checked build inputs. Exact external component revisions remain in their provenance and bundle manifests instead of release-process prose. The macOS arm64 release gate verifies the desktop version sources, builds the Harness, App, DMG, and updater archive, checks the DSH parser plus native and WSL Host launch vectors, relocates the portable Runtime away from its build path, and runs both Harbor entry points before checksumming and publishing. The installer is larger because it carries CPython, Harbor, Codex Auth, Better Sidebar, Context Doctor, and the compressed Node dependency graph; Harbor Jobs still require Docker, Codex Auth remains an unofficial local single-user integration, the model bridge depends on live Docker-to-Host reachability, and an ad-hoc-signed, unnotarized DMG requires manual Gatekeeper approval until Apple release credentials are configured.
